## Stack decision (reasoning, not just the choice)

- **Next.js (App Router, TypeScript, Tailwind)** — already scaffolded.
  Chosen as a genuine full-stack framework: `src/app/**/page.tsx` is the
  frontend, `src/app/api/**/route.ts` is the backend (real server code,
  runs on Node, not "just React"). One deploy target instead of two
  separate services — matters because speed is scored.
- **Deploy: Vercel** (free hobby tier). No cold-start spin-down (unlike
  Render's free tier), single command deploy.
- **DB: Neon** (serverless Postgres, free tier, scales to zero without
  cold-start pain, plugs into Vercel's env vars directly). Use Neon's
  serverless driver (HTTP-based) rather than a raw TCP pool — serverless
  functions opening many short-lived direct Postgres connections will
  exhaust a normal connection limit; this is the one real gotcha with this
  stack and Neon's driver is the documented fix for it.
- **Auth: Auth.js (NextAuth)** — Credentials provider, bcrypt-hashed
  passwords stored via Neon, JWT sessions (stateless, works cleanly with
  serverless). `middleware.ts` gates protected pages (checkout, orders,
  account); API routes check `auth()` server-side. Public browsing/search/
  PDP stays unauthenticated (required — the live link must work signed
  out).
- **Checkout: Stripe test mode** — real Checkout/Elements UI, fake card
  numbers (`4242 4242 4242 4242`), no real money. This is what makes
  checkout feel genuinely complete rather than a fake "Order Placed"
  button, which matters for the UX/UI judging criterion.
